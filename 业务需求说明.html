一、工程意图（为什么做这个系统）

学校活动组织目前依靠线下通知，学生获取信息分散、报名靠人工统计。V1.0 用一个最小可用系统跑通核心业务闭环：

教师线上发布活动 → 学生线上浏览与报名 → 教师查看报名名单。本轮不追求功能数量，只保证这条闭环真实、可信、可演示。

本轮验收依据

  1. 教师发布一个容量为 2 人的活动；
  2. 3 名学生依次报名，第 3 人因满员被拒；
  3. 学生可取消报名，取消后空出名额可再报；
  4. 教师可查看报名名单；活动取消后不可再报名。

二、角色与业务边界

STUDENT 学生

  • 注册 / 登录
  • 浏览活动、查看详情（无需登录）
  • 报名活动、取消报名
  • 查看「我的报名」

TEACHER 教师

  • 登录
  • 发布活动
  • 修改 / 取消自己的活动
  • 查看自己发布的活动
  • 查看活动报名人员名单

V1.0 明确不做

  • 管理员角色、评论、点赞、收藏
  • 消息通知、积分、签到、评价、推荐
  • 文件上传、微信/第三方登录
  • 微服务、Redis、消息队列等复杂中间件

非功能约束

  • 密码必须 BCrypt 加密，绝不存明文
  • 未登录只能浏览，不能报名/发布
  • 教师只能管理自己发布的活动
  • V1.0 不处理并发超卖（人工确认接受）

四、业务规则（R1 ~ R7）——系统的「对错标准」

R1 登录校验：未登录用户只能浏览；报名、发布、管理等操作必须登录，否则 401。
R2 禁止重复报名：同一学生对同一活动只能报名一次。Service 先判断 + 数据库唯一约束双重保障，违反提示「你已报名该活动」。
R3 人数上限：当「已报名人数 ≥ 活动人数上限」时拒绝报名，提示「报名人数已满」。有人取消后名额释放，可再报名。
R4 报名截止：当前时间 ≥ 报名截止时间时拒绝报名，提示「报名已截止」。报名截止时间必须严格早于活动开始时间。
R5 资源所有权：只有活动发布者本人能修改 / 取消该活动、查看其报名名单；其他教师越权操作返回 403。
R6 活动状态：活动被取消（CANCELLED）后不可再报名、不可再修改；取消是状态变更，不删除数据、不删除报名记录。
R7 密码安全：密码使用 BCrypt 单向哈希存储，任何接口都不返回密码字段。

五、每一步简单逻辑（业务流程）

① 注册（F1）

  1. 用户提交：用户名、密码、角色（学生 / 教师）。
  2. 系统校验：用户名 3~50 位且未被占用；密码 6~64 位；角色只能是 STUDENT / TEACHER。
  3. 密码经 BCrypt 加密后写入用户表（R7），返回用户信息（不含密码）。
  4. 失败处理：用户名已存在 / 参数不合法 → 400 并提示原因。

② 登录（F2）

  1. 用户提交用户名、密码。
  2. 系统查到用户并用 BCrypt 比对密码。
  3. 成功：签发 JWT（内含 userId 与 role，24 小时有效）并返回。
  4. 失败：账号不存在或密码错误，统一提示「用户名或密码错误」（不暴露账号是否存在）。

③ 教师发布 / 修改 / 取消活动（F3 / F4）

  1. 必须是 TEACHER 角色，学生调用直接 403。
  2. 校验时间：结束时间 > 开始时间 > 报名截止时间；创建时开始时间必须晚于当前时间。
  3. 创建：写入活动，状态默认为 ACTIVE。
  4. 修改：只能改自己的活动（R5）；已取消不可改；新人数上限不能小于当前已报名人数。
  5. 取消：只能取消自己的活动，把状态改为 CANCELLED，数据与报名记录保留。

④ 学生浏览（F5 / F6，公开）

  1. 无需登录即可查看活动列表与详情。
  2. 列表默认只显示「报名中」活动，已取消的活动不进列表。
  3. 系统按当前时间实时计算活动阶段，并返回「已报名人数 / 人数上限」。
  4. 详情页可打开已取消活动，并明确显示「已取消」。

⑤ 学生报名（F7）——规则最集中的一步

学生点击报名 ↓ 必须登录且为学生（否则 401 / 403） ↓ 活动是否存在？（不存在 → 404） ↓ 活动是否已取消？（R6 → 400「活动已取消，无法报名」） ↓ 是否已过报名截止时间？（R4 → 400「报名已截止」） ↓ 是否已满员？（R3：已报名 ≥ 上限 → 400「报名人数已满」） ↓ 是否已重复报名？（R2 → 400「你已报名该活动」） ↓ 全部通过 → 写入一条报名记录，返回成功

⑥ 学生取消报名（F8）

  1. 必须登录且为学生。
  2. 活动开始前才允许取消（人工确认规则）。
  3. 找到本人的报名记录并删除；没有记录则提示「你未报名该活动」。
  4. 取消后名额立即释放，其他学生可以补报（对应验收第 3 条）。

⑦ 教师查看报名名单（F9）

  1. 必须登录。
  2. 校验该活动是否由当前教师发布（R5），其他教师 / 学生均 403。
  3. 返回报名学生的用户 ID、用户名、报名时间，按报名先后排序。

七、数据模型（3 张表，极简）

表关键字段约束
user 用户id、username、password_hash、role、created_atusername 唯一；role ∈ STUDENT/TEACHER；不存明文密码 (R7)
activity 活动id、teacher_id、title、description、location、start_time、end_time、signup_deadline、max_participants、status、created_atteacher_id 关联发布教师；status ∈ ACTIVE/CANCELLED
registration 报名id、activity_id、student_id、registered_at(activity_id, student_id) 联合唯一（R2 最终防线）
设计原则：业务代码负责「友好的正常判断与提示」，数据库约束负责「最终的数据完整性」，二者不可互相替代。
